# Precision of the block ops (fp16 / bf16)

Applies to `rms_norm`, `rms_norm_mod`, `qk_norm_rope`, `situ_glu`, `gated_residual`,
`token_mse`, the fused linear ops (`linear_situ`, `linear_gated_residual`,
`linear_qk_rope`) and the optimizer step kernels, in every backend (Triton for sm80+ and
XPU, TileLang for sm70 / sm75, the `compile` backend, eager).

## Eager reference and error statistics

- The eager backend (`kohakumoss_kernels/backends/eager`) defines what every op
  computes. It computes in `promote(input, fp32)` and rounds once to the output dtype,
  so the same code run on fp64 inputs is the fp64 reference.
- Error statistics (`kohakumoss_kernels/error_stats.py`; the test check in
  `tests/_util/error_stats.py`, `tests/kernels/blocks/_blockops_harness.py`). For each output
  and input gradient, the kernel and the eager composition in the same dtype are both
  measured against the fp64 reference: cosine similarity, and absolute and relative
  error (|out - ref| / |ref| over the nonzero reference) each as mean / median / min /
  max. Every check appends that table and the worse-list (each summary where the kernel
  is worse than eager) to `$KOHAKUMOSS_PRECISION_DIR/<test>.jsonl`. A test fails only
  on a regression: a non-finite value where eager is finite, or `MAX_ERROR_RATIO` (10)
  x eager or more on the cosine deficit, or on the abs and rel error of the same
  summary (mean, median) together. Max / min never fail; an entry of the worse-list
  gets a written justification or a fix. Among the kernels without a regression, the
  fastest is selected. fp64 exists only in the tests and benches that compute the
  reference.
- Per-sample tensors (`shift`, `scale`, `gate` [B, D], and the q/k weights) are read
  through their strides in every kernel: the backbone passes `mod[:, k]` slices of one
  [B, 6, D] tensor (row stride 6 D) and no backend copies them. The tests build them as
  such slices with distinct rows and keep the layout in their leaves
  (`_blockops_harness._leaf`), and each op has a broken variant that reads a strided
  vector as row-major and must be caught.
- Every test is paired with a broken variant that it must reject (wrong segment, wrong
  axis order, swapped halves, dropped gate, dropped weight, coupled weight decay).

## Arithmetic rules every kernel follows

- Load to fp32, compute in fp32, round once at the store. No intermediate is rounded to
  16 bits inside an op.
- GEMM accumulators are fp32 and the fused epilogue reads the accumulator directly. When
  the backward needs the pre-activation (`linear_situ` saves `[up | gate]`,
  `linear_qk_rope` saves the pre-norm q / k, `linear_gated_residual` saves the projection
  when the gate is trained), the saved copy is the accumulator rounded once; for
  `linear_qk_rope` the norm statistics are taken from that rounded copy so forward and
  backward see the same values.
- Row statistics (`rms_norm*`, `qk_norm_rope`) use IEEE division and square root
  (`tl.div_rn`, `tl.sqrt_rn`; TileLang builds without fast math). `rstd` is kept in fp32 for
  the backward.
- RoPE angles are the fp32 `sin` / `cos` (full-range libdevice on CUDA, no `__sinf`) of
  the fp32 phase `pos * band`, as the eager reference computes them.
- No fp64 anywhere.
- Reductions over rows (`d_weight`, `d_shift`, `d_scale`, `d_gate`, the q/k-norm weight
  gradients) are per-tile partials summed in a fixed order: one program per *segment
  tile* (rows of one sample), then a sum per sample. No atomics, so gradients are
  bit-reproducible run to run. Each tile sums fp32 products row block by row block into
  its partial, one slot per reduced quantity (`rms_norm_mod`: `[T, 2, D]` with slot 0
  the sum of `g x_hat`, slot 1 the sum of `g`), and the per-sample sum adds a sample's
  tile partials of each slot in tile order. An epilogue forms `d_weight = sum_b (1 + scale_b)
  S_gx`, `d_scale = w S_gx`, `d_shift = S_g` in fp32.
- `linear_qk_rope` writes `dq` and `dk` into the two column halves of one `[N, 2 D]`
  buffer and takes `dy = [dq | dk] @ [Wq; Wk]` as a single GEMM: one fp32 accumulation and
  one rounding, where the composition rounds `dq Wq` and `dk Wk` separately and rounds
  their sum again.
- The fused linear ops take weights (and biases) in their storage dtype, fp32 masters
  included (`backends/_master.py`): the matmul operands are cast to the activation dtype
  inside the op, the saved tensor is the master itself (no 16-bit weight copy is kept
  for the backward), and the weight gradient is one GEMM on the 16-bit operands with its
  fp32 accumulator stored straight in the storage dtype (an fp32 master gets the fp32
  result, never a 16-bit rounding first). fp32
  activations under autocast are cast to the autocast dtype first, as autocast casts a
  linear's inputs; the residual stream `x` of `linear_gated_residual` keeps its dtype
  (an fp32 stream with 16-bit projections takes the split path on TileLang).
- The `linear_gated_residual` fused path saves the projection for the gate gradient in
  the activation dtype, as the eager composition does.
- The `token_mse` total is fp32 per row block, the block partials summed in a fixed
  order.
- Nothing clamps. An op returns what the eager reference returns; keeping activations inside the
  fp16 range is the job of the residual-stream fold (`kohakumoss.model.numerics`).

## Optimizer step kernels

- AdamW stores `m` and `r = sqrt(v)`: the squared gradient never reaches 16-bit storage
  (fp16 `v` underflows below 6e-8; its root does not).
- Parameter writeback: `nearest`; `stochastic` (bf16 only: a counter-based 32-bit hash of
  (index, seed) supplies the 16 discarded bits, so the expected value equals the fp32
  update); `kahan` (fp16 or bf16 parameter plus a same-dtype compensation buffer; the
  parameter value is `p + comp`, which follows an fp32 master within one ULP of the
  compensation).
- 8-bit state: blocks of 256 values, `m` as int8 and `r` as uint8 codes of
  `sqrt(|x| / block_absmax)`, which spends the code range on small magnitudes.
- `seed` must advance every step and be identical across data-parallel ranks.

## Kernel or compile, per problem

Each registered op is a `KernelOrCompile` (`backends/compile/choice.py`). Only the
most-prior backend that works for the op on the arch is tuned: its candidates are that
backend's kernel and `torch.compile(eager reference)` (TileLang on sm70 / sm75, Triton on
sm80+ and XPU). A backend that fails to build or run is logged once and the registry falls
back to the next one in the priority, which is then timed the same way; nothing below the
first working backend is built or timed. A call binds, per problem shape, the stored
per-card winner of the two candidates, else the kernel; nothing is timed inside a call, so a forward and its checkpoint recompute always
use the same implementation, and `no_grad` / `inference_mode` calls never run a backward.
`retune_pending()` measures the problems seen so far between steps (forward + backward on
synthetic inputs) through the shared tuner (`select(..., autograd=True)`), so it times
nothing under inference mode, inside a checkpointed forward or a backward, or with
`TUNE=off`; those problems stay queued for the next call. `prewarm_block_ops`
(`backends/compile/prewarm.py`) measures every token bucket before step 0. A kernel that cannot run
on a device (checked once per device under `no_grad`) binds the eager reference there.

The registered compile path is `torch.compile(eager, dynamic=True)`: one graph serves every
token count, so packed batches of changing length never recompile, and a checkpoint
recompute always meets the graph its forward ran. `dynamic=None` would trace the first
length statically and recompile on the second, which is how a recompute pending from an
earlier micro-batch can meet a different graph (`test_kernel_or_compile.py` checks the
graph count).

Each call pattern gets its own compiled callable (`CompiledOp`, `backends/compile/ops.py`),
built from a fresh copy of the eager reference's code object, so each pattern has its own Dynamo
cache and recompile budget. A call pattern is the global state Dynamo guards on (grad mode,
intra-op thread count, autocast dtype) plus, per argument, dtype / requires_grad / rank,
None or the Python scalar.

- Why per pattern: with one cache for every pattern, each new pattern is a recompile.
  - Under LoRA, block 0's input is frozen, so requires_grad differs between blocks.
  - A checkpoint recompute runs on the autograd thread, whose intra-op thread count
    differs from the main thread's.
  - Past `recompile_limit` (8), Dynamo runs the code object eagerly. A checkpointed
    forward that ran compiled then met an eager recompute, and torch.utils.checkpoint
    raised "a different number of tensors was saved".
- No silent eager fallback: each pattern compiles through a counting backend that raises
  `GraphLimitError` past `GRAPH_LIMIT` (8) graphs. Dynamo's own limits are raised to at
  least 64 / 4096, so its silent fallback is never reached first.
- `test_compiled_checkpoint.py` checks the recompute-state call against a one-cache
  variant at the default limit.

The block-op benches
(`scripts/bench/kernel/`) report it as `compile_dyn` next to the static-shape
`torch.compile(eager, dynamic=False)` (`compile`), which is the best case per shape; the
`selected` column is the faster of the kernel and `compile_dyn`.

## Real-model structural tests

The real-weights tests (`tests/integration/`) compare two runs of the same math. On the
42-block MOSS-Image backbone (random latents and text, a few hundred tokens), two valid
implementations of one forward (another problem shape, so another GEMM tiling or another
bound kernel / compile winner) differ by these relative L2 errors (RTX 5090):

| comparison | bf16 | fp16 |
| --- | --- | --- |
| packed batch vs each sample alone | 0.052 | 0.0068 |
| packed batch vs the same batch plus a zero padding sample | 0.050 | 0.0064 |
| gate fold by 2^-4 vs unfolded | 0 (fresh process), 0.040 (other winners bound) | 0.0065 |
| text lengths of two samples swapped (a broken layout) | 0.26 | 0.26 |
| negative skip layers vs every block | 0.43 | 0.43 |

- `test_model_real.py` runs in fp16 with a 2e-2 bound: 3x its rounding noise, 13x below
  the broken layout.
- `test_fold_real.py` runs in bf16, where a power-of-two fold scales every weight exactly:
  folded vs unfolded within 0.12 (3x another binding's 0.040, below the broken
  layout's 0.26), and
  unfolding restores the unfolded output to 1e-6. In fp16 the fold is not invertible:
  weights below 16x the smallest normal lose bits as subnormals.
- `test_sampling_real.py` measures its own noise floor: two-pass CFG run one sample at a
  time against two at a time (0.040-0.048 per sample after one step in bf16; 0.14-0.17
  after four, where the trajectory amplifies it). Packed CFG must lie within 3x that floor
  of two-pass CFG (0.039-0.059 measured); packed CFG fed the positive text in the
  unconditional half moves the latents by 0.70-0.75. The floor is at least the bf16
  rounding scale (2^-7).
- `test_resume_real.py`: the training backward is not bit-reproducible run to run (step 1
  of two identical runs: same loss, gradient norm 0.022149 vs 0.022184), and AdamW
  amplifies the difference on near-zero adapter tensors. After a 4-step LoRA run, the
  median relative difference per checkpoint tensor kind:

  | kind | a second straight run | resumed from step 2 | resumed without the step generators |
  | --- | --- | --- | --- |
  | lora_up | 0.145 | 0.054 | 0.46 |
  | lora_down | 0.013 | 0.0047 | 0.033 |
  | exp_avg | 0.44 | 0.43 | 1.08 |
  | exp_avg_sq | 0.32 | 0.26 | 0.87 |

  The test runs the straight run twice and requires each kind of the resumed run within
  1.5x the second straight run's difference (exact where that is exact); plain values,
  counters and integer tensors must be equal, and the resumed first step's loss must be
  bit-identical.
- `test_train_real.py` compares the step-1 loss and gradient norm across memory
  profiles. At LoRA init (zero up factors) the step-1 gradient norm is very sensitive to
  the batch: the compiled VAE encode (`compile="auto"` compiles a resident VAE only) and
  the eager one give latents that differ by bf16 rounding, and the gradient norm then
  moves by 17-44% between profiles (0.0318 vs 0.0178). With the eager encode in every
  profile, `balanced` and `minimal` agree to 0.1% (0.017770 vs 0.017790), so the test
  runs every profile with `VAE_ENCODE={"compile": "off"}`.
- `test_adapters_real.py` checks one adapted layer's error statistics against fp64
  (`tests/_util/error_stats.py`), whose rounding-scale floors (bf16 eps 2^-7, 10x) pass a
  dropped delta of a few percent. Its layer adapter gets noise of std 0.1 before the
  check, a delta about the size of the base weight, so a dropped delta moves the output
  far past those floors and fails the check.
