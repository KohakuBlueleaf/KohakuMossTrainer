# Precision of the block ops (fp16 / bf16)

Applies to `rms_norm`, `rms_norm_mod`, `qk_norm_rope`, `situ_glu`, `gated_residual`,
`token_mse`, the fused linear ops (`linear_situ`, `linear_gated_residual`,
`linear_qk_rope`) and the optimizer step kernels, in every backend (Triton for sm80+ and
XPU, TileLang for sm70 / sm75, the `compile` backend, eager).

## The spec and the bar

- The eager backend (`kohakumoss_kernels/backends/eager`) is the definition. It computes in
  `promote(input, fp32)` and rounds once to the output dtype, so the same code run on
  fp64 inputs is the reference.
- A backend passes when its error against that fp64 reference is at most 1.1x the error of
  the eager spec run in the same dtype, in both the elementwise-max and the RMS metric, for
  the output and every input gradient (`kohakumoss_kernels/precision.py`,
  `tests/kernels/_blockops_harness.py`), every dtype including fp32. The one other way to
  pass is to be correctly rounded: every element within half a ULP of the fp64 reference
  in the result's own dtype. No implementation can be more precise than that, and when the
  eager error is itself below half a ULP (a scalar sum that happens to round right) the
  ratio would only measure luck. There is no other floor.
- Per-sample tensors (`shift`, `scale`, `gate` [B, D], and the q/k weights) are read
  through their strides in every kernel: the backbone passes `mod[:, k]` slices of one
  [B, 6, D] tensor (row stride 6 D) and no backend copies them. The tests build them as
  such slices with distinct rows and keep the layout in their leaves
  (`_blockops_harness._leaf`), and each op has a broken variant that reads a strided
  vector as row-major and must be caught.
- Every test is paired with a broken variant that it must reject (wrong segment, wrong
  axis order, swapped halves, dropped gate, dropped weight, coupled weight decay).

## Arithmetic rules every kernel follows

- Load to fp32, compute in fp32, round once at the store. No intermediate is rounded to
  16 bits inside an op.
- GEMM accumulators are fp32 and the fused epilogue reads the accumulator directly. When
  the backward needs the pre-activation (`linear_situ` saves `[up | gate]`,
  `linear_qk_rope` saves the pre-norm q / k, `linear_gated_residual` saves the projection
  when the gate is trained), the saved copy is the accumulator rounded once; for
  `linear_qk_rope` the norm statistics are taken from that rounded copy so forward and
  backward see the same values.
- Row statistics (`rms_norm*`, `qk_norm_rope`) use IEEE division and square root
  (`tl.div_rn`, `tl.sqrt_rn`; TileLang builds without fast math). `rstd` is kept in fp32 for
  the backward.
- RoPE angles are the fp32 `sin` / `cos` (full-range libdevice on CUDA, no `__sinf`) of
  the rounded phase `ph = fl(pos * band)` plus the first-order term of its rounding
  error: with `pl = fma(pos, band, -ph)` (exact), `sin = fma(cos(ph), pl, sin(ph))` and
  `cos = fma(-sin(ph), pl, cos(ph))`. The spec's fp32 phase is off by up to half an
  ULP of the phase (2^-13 at position 4000), which the correction removes; what is left
  is the fp32 sin / cos error (about one ULP).
- No fp64 anywhere (`tests/rules/test_no_fp64.py`). Where fp32 is not enough, the kernels
  use double-float: an unevaluated pair `hi + lo` of fp32 values, about 48 significand
  bits. Products are exact pairs (`two_prod` via FMA, Dekker), sums are pair additions
  (`two_sum`, Knuth), division by a count and `rsqrt` (fp32 seed plus one Newton step in
  pairs) keep the pair. Triton kernels with pair arithmetic build with
  `enable_fp_fusion=False`; TileLang kernels use the IEEE round-to-nearest intrinsics
  (`T.ieee_add`, `T.ieee_mul`, `T.ieee_fmaf`), so no product is contracted into a sum.
- Reductions over rows (`d_weight`, `d_shift`, `d_scale`, `d_gate`, the q/k-norm weight
  gradients) are per-tile partials summed in a fixed order: one program per *segment
  tile* (rows of one sample), then a pair sum per sample. No atomics, so gradients are
  bit-reproducible run to run. Partials are stored as two fp32 planes (hi, lo) and
  summed as pairs; an epilogue forms `d_weight = sum_b (1 + scale_b) S_gx`,
  `d_scale = w S_gx`, `d_shift = S_g` in pairs and rounds each once. The per-element
  arithmetic is `KOHAKUMOSS_REDUCE` (`kohakumoss_kernels/reduce.py`):
  - `df` (default): exact products, pair sums, and the row statistic recomputed as a
    pair. Triton reduces each row tile with a pair tree (`tl.reduce` with `df_add`).
    TileLang's row statistic over 16-bit inputs, where `x * x` is exact in fp32, is an
    exact hi/lo split sum: each square is split on the grid of `sigma = 2^(ceil(log2
    max) + ceil(log2 D) + 2)` (`(v + sigma) - sigma`); the high parts sum exactly in any
    order and the low parts are below one ULP of sigma. The result is correctly rounded
    against the fp64 reference on cancelling sums (`tests/kernels/test_df_reduce.py`);
    the q/k-norm weight gradients are within the fp32 sin / cos accuracy.
  - `kahan`: fp32 products, fp32 tile sums, Kahan compensation across tiles (stored as
    the pair `(s, -c)`); cheaper, about one rounding per term.
- `linear_qk_rope` writes `dq` and `dk` into the two column halves of one `[N, 2 D]`
  buffer and takes `dy = [dq | dk] @ [Wq; Wk]` as a single GEMM: one fp32 accumulation and
  one rounding, where the composition rounds `dq Wq` and `dk Wk` separately and rounds
  their sum again.
- The fused linear ops take weights (and biases) in their storage dtype, fp32 masters
  included (`backends/_master.py`): the matmul operands are cast to the activation dtype
  inside the op, the saved tensor is the master itself (no 16-bit weight copy is kept
  for the backward), and the weight gradient is one GEMM with fp32 accumulation and fp32
  output (`torch.mm(..., out_dtype=float32)`) rounded once to the storage dtype. fp32
  activations under autocast are cast to the autocast dtype first, as autocast casts a
  linear's inputs; the residual stream `x` of `linear_gated_residual` keeps its dtype
  (an fp32 stream with 16-bit projections takes the split path on TileLang).
- The elementwise-max metric of `dy` and of the weight gradients behind a 16-bit GEMM is
  dominated by the rounding of the GEMM's 16-bit operand (`dq`, `dk`, `do`), which the
  composition shares; over 24 seeds of the `linear_qk_rope` test (V100, fp16) the `dy`
  ratio to eager has median 0.97 and exceeds 1.1 in 29 % of seeds, while the RMS ratio is
  0.97 at most in every seed.
- The `linear_gated_residual` fused path saves the projection for the gate gradient in
  fp32 (`KOHAKUMOSS_GATE_SAVE`, default `fp32`): the eager composition's gate gradient
  uses cuBLAS's 16-bit projection, so a 16-bit copy from a different GEMM order differs
  from it element by element; the fp32 copy is closer to the reference than either.
- The `token_mse` total is double-float throughout (`two_sum` difference, pair squares,
  pair partials) and rounds once.
- fp32 inputs to the Triton `rms_norm_mod` in `df` mode (the `fp32_residual` stream)
  compute the forward and `d_x` in pairs and round once, so they are correctly rounded
  too; `kahan` mode keeps them in plain fp32.
- Nothing clamps. An op returns what the spec returns; keeping activations inside the
  fp16 range is the job of the residual-stream fold (`kohakumoss.model.numerics`).

## Optimizer step kernels

- AdamW stores `m` and `r = sqrt(v)`: the squared gradient never reaches 16-bit storage
  (fp16 `v` underflows below 6e-8; its root does not).
- Parameter writeback: `nearest`; `stochastic` (bf16 only: a counter-based 32-bit hash of
  (index, seed) supplies the 16 discarded bits, so the expected value equals the fp32
  update); `kahan` (fp16 or bf16 parameter plus a same-dtype compensation buffer; the
  parameter value is `p + comp`, which follows an fp32 master within one ULP of the
  compensation).
- 8-bit state: blocks of 256 values, `m` as int8 and `r` as uint8 codes of
  `sqrt(|x| / block_absmax)`, which spends the code range on small magnitudes.
- `seed` must advance every step and be identical across data-parallel ranks.

## Kernel or compile, per problem

Each registered op is a `RacedOp` (`backends/compile/race.py`). A call binds, per problem
shape, the stored per-card winner of kernel vs `torch.compile(eager spec)`, else the
kernel; nothing is timed inside a call, so a forward and its checkpoint recompute always
use the same implementation, and `no_grad` / `inference_mode` calls never run a backward.
`retune_pending()` measures the problems seen so far between steps (forward + backward on
synthetic inputs) through the shared tuner (`select(..., autograd=True)`), so it times
nothing under inference mode, inside a checkpointed forward or a backward, or with
`TUNE=off`; those problems stay queued for the next call. `prewarm_block_ops`
(`backends/compile/prewarm.py`) measures every token bucket before step 0. A kernel that cannot run
on a device (checked once per device under `no_grad`) binds the eager spec there.

The registered compile path is `torch.compile(eager, dynamic=True)`: one graph serves every
token count, so packed batches of changing length never recompile, and a checkpoint
recompute always meets the graph its forward ran. `dynamic=None` would trace the first
length statically and recompile on the second, which is how a recompute pending from an
earlier micro-batch can meet a different graph (`test_race.py` checks the graph count). The block-op benches
(`scripts/bench/kernel/`) report it as `compile_dyn` next to the static-shape
`torch.compile(eager, dynamic=False)` (`compile`), which is the best case per shape; the
`selected` column is the race between the kernel and `compile_dyn`.
